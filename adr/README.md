# Architecture Decision Records

ADRs record significant, durable architecture decisions.

## Naming

Use `ADR-NNN-short-title.md`.

## Status

`proposed`, `accepted`, `superseded`, or `deprecated`.

## When an ADR is required

Use an ADR when a change affects system structure, domain boundaries, tenant isolation, data architecture, storage strategy, communication semantics, security model, runtime/deployment, reliability, external contracts, or long-term evolution.

Do not create ADRs for trivial local implementation choices.

## Principle

An ADR documents why a decision is justified. A technology name without context, alternatives, consequences, and requirements is not an architecture decision.
