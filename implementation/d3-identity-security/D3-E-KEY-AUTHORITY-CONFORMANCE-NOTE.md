# D3-E Key Authority Conformance Note

**Status:** evidence-branch design note; no D3/D3-E/Wave 4/production/D4 authority is granted by this file  
**Baseline:** `main@30ca7b72c7ea2810389d87c94ec5752e45620548`  
**Candidate under test:** OpenBao `2.6.2` Transit behind a provider-neutral key-authority port

## Why this note exists

D3-E is the only nonterminal D3 track after D3-B conformance. Six evidence obligations remain:

1. `revocation_and_replay`;
2. `key_authority_provider_port_conformance`;
3. `stale_restored_key_epoch_rejected`;
4. `replay_single_winner_concurrency`;
5. `rotation_overlap_and_pre_rotation_snapshot_nonresurrection`;
6. `source_lifecycle_state_not_replaced_by_derived_state`.

The source contracts require more than proving that a KMS can compute cryptographic operations. They require that provider state remain subordinate to JLMirror source lifecycle/currentness authority, that replay admission be atomic single-winner, and that stale restored key objects never self-certify current authority.

## Candidate capability finding

`OPEN-REL-016` currently states the message-equivalence domain-separation mechanism as an HKDF-derived per-scope subkey from a platform master key. OpenBao Transit supports versioned HMAC operations, but its HMAC API does not expose the context-derived HMAC primitive needed to implement that exact shape while keeping the derived HMAC key entirely inside Transit.

D3-E MUST NOT paper over that gap by using one shared Transit HMAC key and concatenating tenant/scope into the HMAC input. That would recreate the exact single-key equality-oracle failure that `OPEN-REL-016` forbids.

The bounded OpenBao conformance profile therefore uses **independent, non-exportable provider key objects per canonical cryptographic key domain**. The domain is the canonical tuple:

```text
(tenant_id, message_identity_scope, erasure_unit)
```

The provider key reference is deterministically derived from the canonical domain identifier, but the cryptographic key material itself is independently generated by the key authority. The MAC input contains only the immutable comparison message; tenant/scope separation is in the selected key material, not merely in a query predicate or input prefix.

This is at least as strong as HKDF-derived subkeys for cross-domain equality isolation, but it has a different provider-object-cardinality cost. Therefore:

- HKDF remains the reference/default derivation strategy where a selected key-authority backend can perform it inside the trusted key boundary;
- independently generated non-exportable key objects per the same canonical domain are the OpenBao bounded-evidence strategy;
- a shared key with domain folded only into the MAC input remains prohibited;
- provider-key cardinality, production topology and rotation/recovery timing remain C3 and are **not** selected by this D3 evidence;
- `OPEN-REL-016` normative wording must be reconciled with this equivalent key-material-separation mechanism before D3-E evidence can be promoted.

## Provider-neutral port boundary

The D3-E harness SHALL make the backend replaceable. Callers operate on logical key domains/generations and cryptographic intents, never OpenBao paths, tokens, namespaces, storage layout or provider-native currentness.

The port must prove at least:

- logical-domain -> provider-key mapping is canonical and not caller-selected provider authority;
- HMAC/sign/verify operations are explicit about logical generation;
- keys used by runtime operations are non-exportable and plaintext key backup/export endpoints are not part of the port;
- provider-reported latest generation cannot override JLMirror lifecycle state;
- source lifecycle may designate current, overlap/historical-verification-only and retired generations independently of provider reachability;
- a restored provider containing an old usable key remains stale until source lifecycle/currentness authorizes it.

## Recovery model under test

The negative control must be a **genuine provider restore**, not an empty cache or a mocked missing key:

1. initialize OpenBao with persistent encrypted storage;
2. create non-exportable key material at generation 1;
3. stop the provider and copy its encrypted-at-rest storage as a pre-rotation snapshot;
4. restart, rotate to generation 2 and advance JLMirror source lifecycle;
5. exercise explicit previous-generation verification overlap without permitting old-generation issuance;
6. retire generation 1 in source lifecycle;
7. restore the pre-rotation OpenBao storage snapshot, where generation 1 is genuinely usable by the raw provider;
8. prove the JLMirror port rejects that stale provider/currentness and does not let restored generation 1 become current authority.

The provider snapshot is not the source lifecycle database. `KEY OBJECT RESTORED != KEY AUTHORITY CURRENT` remains the controlling law.

## Replay model under test

`private_key_jwt` replay admission is a Security authority independent of cryptographic signature validity.

The harness SHALL prove:

- concurrent create-or-observe of one `(client_principal, jti)` across separate replay-ledger connections has exactly one winner;
- unavailability/uncertain replay continuity fails closed;
- a restored replay store cannot turn a previously relevant assertion into unused state;
- continuity loss is fenced by a trusted source generation/current credential disposition before token issuance can resume;
- valid signature/key reachability never substitutes for replay admission.

## Source lifecycle vs derived/read-model state

A deliberately stale derived key-status view will be injected during the tests. It may claim an old generation is current, but issuance/verification admission must still consult the source lifecycle authority. The derived view is diagnostic/acceleration state only.

## Authority boundary

This branch is source evidence only until all of the following occur on an exact HEAD:

- pinned OpenBao conformance succeeds;
- all six remaining D3-E vectors are demonstrated by actual negative controls;
- deterministic/native assurance is green;
- fresh adversarial Codex review is clean;
- the binding `OPEN-REL-016` wording is reconciled without weakening cryptographic domain separation;
- a separate promotion changes the machine-owned D3-E evidence ledger.

Even after D3-E becomes `per_track_conformed`, D3 global acceptance is a separate governed event. Wave 4, production, D4 and C3 numerics/topology are not implied.
